# CI Production Build Audit

## Problem

CI performance and PHPUnit timing evidence is only useful when the jobs run the
same production build shapes on every branch. Earlier slices moved the normal,
embedded, WordPress, and clang-tools workflow paths to production presets and
added `Release`/`MinSizeRel` cache guards, but that protection was implicit in
the workflow text. A later workflow edit could accidentally reintroduce a
developer preset or an unguarded WordPress timing path, making the branch/main
performance comparison misleading again.

## Source Findings

- Base: MariaDB `mariadb-11.8.6`
  (`9bfea48ce1214cc4470f6f6f8a4e30352cef84e7`). This slice does not change
  MariaDB source or runtime behavior.
- `CMakePresets.json` defines developer presets (`dev`, `embedded-dev`,
  `php-embedded-dev`) and production presets (`prod`, `embedded-prod`,
  `php-embedded-prod`, `ownerless-test-hooks`, `ownerless-stress`).
- `.github/workflows/ci.yml` currently configures, builds, tests, formats, and
  runs clang-tidy through production presets. Embedded and WordPress timing
  steps repeat `tools/require-cmake-release-build` for MyLite build trees and
  `tools/require-cmake-build-type MinSizeRel` for MariaDB embedded archives.
- The WordPress job sets
  `MYLITE_WORDPRESS_CMAKE_BUILD_DIR=build/wordpress-php-embedded-prod`,
  `MYLITE_WORDPRESS_CMAKE_BUILD_TYPE=Release`, and
  `MYLITE_WORDPRESS_REQUIRE_RELEASE_BUILD=1`, then repeats the cache guards
  inside dependency, database-prep, performance-probe, and PHPUnit test-only
  steps.
- `tools/CMakeLists.txt` already registers first-party tool checks in CTest, so
  a workflow audit can be exercised by the production CTest preset as well as
  directly by GitHub Actions.

## Design

Add `tools/check-ci-production-builds`, a small static workflow audit that:

- rejects `cmake` or `ctest` invocations in `.github/workflows/ci.yml` that use
  `dev`, `embedded-dev`, or `php-embedded-dev` presets;
- rejects old developer build directories such as `build/dev`,
  `build/embedded-dev`, `build/php-embedded-dev`, and
  `build/wordpress-php-embedded`;
- requires production configure/build/test markers for `prod` and
  `php-embedded-prod`;
- requires `format-check-prod` and `tidy-prod`;
- requires the explicit production-build audit step to remain present in all
  current CMake-backed CI jobs;
- requires the visible MyLite `Release` guards and MariaDB embedded
  `MinSizeRel` guards;
- requires the WordPress Release-build and external database timing settings;
- requires the WordPress PHPUnit Docker-image, fetch, PHP-extension build,
  dependency, database-prep, perf-probe, and test-only suite steps to remain
  separate visible CI phases;
- rejects the WordPress harness `all` phase and the old single
  `Run WordPress PHPUnit suite` step name in CI timing paths;
- requires production WordPress PHPUnit phases to keep harness-owned JUnit
  timing enabled, so CI logs include slowest class and method summaries;
- requires the process-isolated child profiling and defensive static `wpdb`
  scan defaults to stay disabled for CI timing;
- rejects the stale broad isolated-class filter and requires exact
  method-level process-isolated WordPress PHPUnit shard markers, so mixed
  classes do not inflate process-isolated timings with ordinary tests;
- requires the embedded ownerless SQL and embedded performance probes to run
  from `build/php-embedded-prod`.

Run this audit as an explicit workflow step after checkout in each CMake-backed
CI job and register it as `tools.ci-production-builds` in CTest. The per-job
workflow step catches CI drift before job-specific build/test timing starts;
the CTest registration keeps local `ctest --preset prod` and CI
`ctest --preset prod` runs honest.

This is deliberately a workflow guard, not a YAML schema parser. It checks the
project-specific invariants that matter for timing fidelity and fails with the
matching workflow lines when a forbidden pattern is present.

## Compatibility Impact

No SQL, C API, PHP API, mysqli behavior, storage format, ownerless runtime, or
directory lifecycle changes. This slice changes CI/test governance only.

## Build And Performance Impact

No production compiler flags change. The audit runs `grep` over one workflow
file and adds negligible CI overhead. Its purpose is to prevent performance
logs from being generated by non-production build trees.

## Acceptance Criteria

- CI has a visible production-build audit step after checkout in the normal
  build, embedded, WordPress PHPUnit, and clang-tools jobs.
- Production CTest runs include the same audit.
- The audit fails if CMake-backed CI uses developer presets, developer build
  directories, missing production guard calls, missing WordPress Release timing
  settings, an all-in-one WordPress harness phase, or a collapsed PHPUnit suite
  step that hides test timing inside setup/build work.
- The audit fails if production WordPress PHPUnit phases disable the JUnit
  slow-test timing report.
- The audit fails if the WordPress job reintroduces the stale broad
  process-isolated class filter or removes representative exact method-level
  process-isolated shard markers.
- Documentation makes clear that local developer compatibility commands may use
  `embedded-dev`, but CI timing evidence must use production presets and pass
  the audit.
